# Описание таблиц

---

## APP_USER

**Назначение:** базовая учётная запись. Хранит данные аутентификации и роль.

**Функциональные зависимости:**

```
{user_id} -> email, password_hash, role, created_at, updated_at
{email}   -> user_id, password_hash, role, created_at, updated_at
```

**Нормальные формы:**
- 1НФ: все значения атомарны
- 2НФ: PK не составной, частичных зависимостей нет
- 3НФ: нет транзитивных зависимостей
- НФБК: детерминанты `user_id` и `email` — потенциальные ключи

---

## EMPLOYER_PROFILE

**Назначение:** профиль работодателя (компании). 1:1 к `APP_USER` при `role = 'employer'`.

**Внешний ключ:** `user_id -> APP_USER(user_id)`.

Соответствие типа профиля роли пользователя проверяется триггером:
`EMPLOYER_PROFILE` может быть создан только для пользователя с `role = 'employer'`.
При изменении роли пользователя также проверяется отсутствие несовместимого профиля.

**Функциональные зависимости:**

```
{user_id} -> company_name, description, website, created_at, updated_at
```

**Нормальные формы:** 1НФ, 2НФ, 3НФ, НФБК.

---

**Внешний ключ:** `user_id -> APP_USER(user_id)`.

При изменении роли пользователя также проверяется отсутствие несовместимого профиля.

**Функциональные зависимости:**

```

**Нормальные формы:** 1НФ, 2НФ, 3НФ, НФБК.

**Функциональные зависимости:**

```
{category_id} -> name, created_at, updated_at

```

**Нормальные формы:** 1НФ, 2НФ, 3НФ, НФБК.

## VACANCY

**Назначение:** инвариантные поля вакансии. Изменяемые данные (title, description, salary) хранятся в `VACANCY_HISTORY`.

**Функциональные зависимости:**

```
{vacancy_id} -> employer_id, created_at
```

**Нормальные формы:** 1НФ, 2НФ, 3НФ, НФБК.

---

## VACANCY_CATEGORY

**Назначение:** связующая таблица M:N между `VACANCY` и `CATEGORY`.

**Функциональные зависимости:** нет неключевых атрибутов.

**Нормальные формы:** 1НФ, 2НФ, 3НФ, НФБК.

---

## VACANCY_HISTORY

**Назначение:** все версии вакансии. Актуальная версия — с максимальным `version`.

**Функциональные зависимости:**

```
{vacancy_id, version} -> title, description, salary_from, salary_to, changed_at
```

**Нормальные формы:**
- 1НФ
- 2НФ: все неключевые атрибуты зависят от полного ключа `{vacancy_id, version}`
- 3НФ: нет зависимостей между неключевыми атрибутами
- НФБК: единственный детерминант — потенциальный ключ

### Сохранение истории вакансии

Создание вакансии и её первой версии выполняется в одной транзакции:

1. создаётся запись в `VACANCY`;
2. полученный `vacancy_id` используется для создания записи
   `VACANCY_HISTORY` с `version = 1`.

При изменении вакансии существующая запись `VACANCY_HISTORY` не изменяется.
Вместо этого создаётся новая версия с номером `version + 1`.

Определение номера следующей версии и её добавление выполняются в одной
транзакции. Для предотвращения конкурентного создания одинаковых версий
строка соответствующей вакансии блокируется на время операции.

Таким образом, предыдущие версии остаются неизменными, а `APPLICATION`
ссылается на конкретную версию вакансии.

```
{chat_id}        -> application_id, created_at

## MESSAGE

**Назначение:** сообщения чата.

**Функциональные зависимости:**

```
{message_id} -> chat_id, sender_id, body, is_read, created_at, updated_at
```

**Нормальные формы:** 1НФ, 2НФ, 3НФ, НФБК.

Отправителем сообщения может быть только один из участников соответствующего
отклика: работодатель вакансии или владелец резюме. Это ограничение
проверяется триггером перед добавлением или изменением сообщения.

## Обоснование временных полей

Временные поля добавлены только в те таблицы, где они отражают значимое состояние сущности.

- `VACANCY_CATEGORY`, `RESUME_CATEGORY` — связующие M:N-таблицы без изменяемых неключевых атрибутов, поэтому `updated_at` не требуется. `created_at` также не используется, так как момент добавления категории в текущей модели не является значимым.
- `VACANCY_HISTORY`, `APPLICATION_STATUS_HISTORY` — исторические таблицы. Их записи не изменяются после создания, а время события уже хранится в `changed_at`, поэтому отдельные `created_at` и `updated_at` избыточны.
- `VACANCY` — изменяемые данные вакансии хранятся в `VACANCY_HISTORY`, поэтому самой таблице достаточно `created_at`.
- `FAVORITE_VACANCY` — запись представляет факт добавления вакансии в избранное и либо существует, либо удаляется, поэтому `updated_at` не требуется.
- `PDF_DOCUMENT` — созданный документ не изменяется, поэтому достаточно `created_at`.
- `CHAT` — после создания связь чата с откликом не изменяется, поэтому достаточно `created_at`.
- `NOTIFICATION` и `MESSAGE` содержат изменяемое поле `is_read`, поэтому для них используется `updated_at` для фиксации времени последнего изменения записи.

Поле `updated_at` обновляется приложением при изменении записи.

---

## Обоснование значений по умолчанию

`DEFAULT` используется для технических значений, которые однозначно определяются
в момент создания записи.

- Для `created_at`, `updated_at` и `changed_at` используется `DEFAULT NOW()`,
  так как при создании записи начальным значением является текущее время.
- Для `is_read` используется `DEFAULT FALSE`, так как новое сообщение или
  уведомление изначально считается непрочитанным.
- Идентификаторы создаются автоматически с помощью `GENERATED ALWAYS AS IDENTITY`.
- Для пользовательских и предметных данных (`email`, `role`, названия, текст,
  зарплата и внешние ключи) значения по умолчанию не задаются: обязательные
  значения должны передаваться явно, а необязательные могут оставаться `NULL`.
- Для `version` значение по умолчанию не задаётся, поскольку номер версии
  определяется при создании новой записи истории вакансии.

## Обоснование нормальных форм

### 1НФ

Все атрибуты таблиц содержат атомарные значения. Повторяющиеся группы и
массивы значений внутри одного поля не используются. Связи M:N вынесены
в отдельные отношения `VACANCY_CATEGORY` и `RESUME_CATEGORY`.

### 2НФ

Для отношений с простым первичным ключом частичные функциональные зависимости
невозможны.

Для отношений с составными ключами:

- `VACANCY_HISTORY` имеет ключ `(vacancy_id, version)`. Атрибуты `title`,
  `description`, `salary_from`, `salary_to`, `changed_at` относятся к конкретной
  версии конкретной вакансии и зависят от всей пары.
- `VACANCY_CATEGORY` имеет составной ключ `(vacancy_id, category_id)` и не
  содержит неключевых атрибутов.
- `RESUME_CATEGORY` имеет составной ключ `(resume_id, category_id)` и не
  содержит неключевых атрибутов.
- `FAVORITE_VACANCY` имеет составной ключ `(user_id, vacancy_id)`;
  `created_at` характеризует именно факт добавления конкретной вакансии
  конкретным пользователем.

### 3НФ

В отношениях отсутствуют зависимости неключевых атрибутов от других
неключевых атрибутов. Предметные сущности, справочники и связи между ними
разделены по отдельным отношениям.

### НФБК

Для всех нетривиальных функциональных зависимостей детерминант является
потенциальным ключом.

Отдельные случаи:

- В `APPLICATION` существуют два потенциальных ключа:
  `application_id` и `(vacancy_id, resume_id)`. Оба однозначно определяют
  остальные атрибуты отношения.
- В `VACANCY_HISTORY` детерминантом является полный составной ключ
  `(vacancy_id, version)`.
- В `CATEGORY` потенциальными ключами являются `category_id` и `name`.
- В `CHAT` потенциальными ключами являются `chat_id` и `application_id`,
  так как для одного отклика допускается не более одного чата.
- В профильных таблицах постоянный атрибут `role` не хранится.
  Роль находится только в `APP_USER`, а её соответствие типу профиля
  контролируется ограничениями целостности.
